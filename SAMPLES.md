# Sample artifacts: the file formats extraction reads and writes

[ALGORITHM.md](ALGORITHM.md) explains *how* the extractor works, stage by stage.
This document explains *what it works on*: the file formats it consumes and
produces. Each one gets the same four questions answered — what writes it, what
it is for, how it is structured, and which stage reads which field out of it —
with a real sample to make the structure concrete.

| Doc | Role |
|---|---|
| [SUMMARY.md](SUMMARY.md) | Executive summary — value, and the process end to end |
| [README.md](README.md) | Quickstart — run the thing |
| [TUTORIAL.md](TUTORIAL.md) | Learn the concepts and the APIs, hands-on |
| [ALGORITHM.md](ALGORITHM.md) | Reference — every stage, input/output/algorithm |
| [GLOSSARY.md](GLOSSARY.md) | Canonical vocabulary, shared by the code and every document |
| **SAMPLES.md** (you are here) | The file formats, and real samples of each |

Samples come from one real run against `samples/basic`
(`guess --with-tests --verify`), with `samples/complex_deep` supplying cases
`basic` has no example of. Long absolute paths are shortened to `…`; samples are
trimmed to the fields under discussion, never edited.

## The formats at a glance

The extractor reads **six** input formats and writes **two**. Every input is
machine-generated by a tool that had already done the work — which is the whole
design: [ground truth](GLOSSARY.md#4-this-project) over re-derivation.

| Format | Syntax | Written by | Authority for | Read at |
|---|---|---|---|---|
| [Query stub](#11-the-query-stub) | empty file, meaningful name | you | — (it is a request) | Stage 1 |
| [`index-*.json`](#12-index-json) | JSON | CMake File API | where the other replies are | Stage 1 |
| [`codemodel-v2-*.json`](#13-codemodel-v2-json) | JSON | CMake File API | the directory tree, the target list | Stages 1, 4 |
| [`target-*.json`](#14-target-json) | JSON | CMake File API | link edges, sources, include roots, artifacts | Stages 2, 5, 6, 7, 8, 9 |
| [`directory-*.json`](#15-directory-json) | JSON | CMake File API | per-directory detail (unused today) | — |
| [command trace](#part-2--the-command-trace) | JSON Lines | `cmake --trace-format=json-v1` | the dependency boundary | Stage 3 |
| [CTest registry](#part-3--the-ctest-registry) | JSON on stdout | `ctest --show-only=json-v1` | which executables are registered tests | Stage 7 |
| [`*.o.d` depfile](#42-the-od-depfile) | Makefile rule | `g++ -MMD` | the header closure | Stage 10 |
| [`flags.make`](#41-flagsmake) | Makefile fragment | CMake generator | *(cross-check only)* | — |
| [`link.txt`](#43-linktxt) | shell command | CMake generator | *(cross-check only)* | — |
| **output** `CMakeLists.txt` | CMake | **the extractor** | what the standalone tree builds | Stage 12 |
| **output** `README.md` | Markdown | **the extractor** | documentation, not build control | Stage 13 |

Two formats in that table are deliberately *not* read: `flags.make` and
`link.txt`. Both restate things the File API already reports, and both are
generator-specific — they exist under Unix Makefiles but not under Ninja. They
appear here because they make the File API's answers legible, not because the
extractor depends on them.

One format is conspicuously absent: **`CMakeLists.txt` is never parsed**.
[Part 5](#part-5--cmakeliststxt-as-input) explains why that is a design
commitment rather than an omission.

# Part 1 — The CMake File API

The File API is a **file-based request/response protocol**, not a callable
library. You write a request into a query directory, re-run CMake, and read
replies out of a reply directory. Everything under `<build>/.cmake/api/v1/`
belongs to it.

## 1.1 The query stub

**Written by:** you (the extractor, in `load_codemodel()`) · **Read by:** CMake

**Purpose.** To ask for something. The File API has no command-line interface;
the *existence of a file with a particular name* is the entire request.

**Structure.** There is none — the file is empty, and can stay empty forever. The
name carries the request: `<object-kind>-v<major-version>`. `codemodel-v2` asks
for the codemodel, version 2. Other kinds exist (`cache-v2`, `cmakeFiles-v1`,
`toolchains-v1`); the extractor needs only the codemodel.

**Use in extraction.** Stage 1 creates it before reconfiguring, then never looks
at it again. Creating it is idempotent, which is why the extractor can run any
number of times against the same build directory.

```
build/.cmake/
├── extract-trace.json                        Part 2
└── api/v1/
    ├── query/codemodel-v2                    the request — 0 bytes
    └── reply/                                CMake's answers
        ├── index-2026-09-04T19-27-29-0762.json      start here
        ├── codemodel-v2-ec8d6a201fc97d6f8205.json
        ├── directory-libs.rng-….json   directory-apps.guess-….json   …
        └── target-guess-….json  target-rng-….json  target-fmt-….json  …
```

**Gotcha.** The reply directory is only written when CMake actually re-runs. A
build that is already configured still needs a reconfigure for the reply to
appear — which is why Stage 1 runs `cmake <build>` rather than assuming.

## 1.2 `index-*.json`

**Written by:** CMake, once per configure · **Read at:** Stage 1

**Purpose.** To be the one filename in the reply directory you can predict. Every
other reply is content-hashed, so the index is the only stable entry point.

**Structure.** Two parts matter. `cmake` reports the version and generator that
produced the reply — worth checking, because available fields depend on the
version. `objects[]` is a routing table: one entry per requested object kind,
each naming the file that holds it.

**Use in extraction.** Stage 1 sorts the `index-*.json` files by name, takes the
newest, finds the `objects[]` entry whose `kind` is `codemodel`, and follows its
`jsonFile`. That is the only navigation step; everything after it is a direct
read.

```json
{
  "cmake": {
    "generator": {
      "multiConfig": false,
      "name": "Unix Makefiles"
    },
    "paths": {
      "cmake": "/usr/bin/cmake",
      "cpack": "/usr/bin/cpack",
      "ctest": "/usr/bin/ctest",
      "root": "/usr/share/cmake-3.28"
    },
    "version": {
      "isDirty": false,
      "major": 3,
      "minor": 28,
      "patch": 3,
      "string": "3.28.3",
      "suffix": ""
    }
  },
  "objects": [
    {
      "jsonFile": "codemodel-v2-ec8d6a201fc97d6f8205.json",
      "kind": "codemodel",
      "version": {
        "major": 2,
        "minor": 6
      }
    }
  ],
  "reply": {

```

**Gotcha.** Never glob for `codemodel-v2-*.json` directly. The hash changes on
every configure, and stale replies from earlier runs are *not* removed — a glob
can match several files of different ages. Timestamped index names sort
correctly, which is why "newest index" is well defined.

## 1.3 `codemodel-v2-*.json`

**Written by:** CMake File API · **Read at:** Stages 1 and 4

**Purpose.** To describe the shape of the configured build: which directories it
is assembled from, and which targets exist in each. It is an index, not a
detailed account — per-target substance lives in the target files it points at.

**Structure.** Three keys carry everything:

- `paths` — absolute `source` and `build` roots. Every relative path elsewhere in
  the File API is relative to one of these two.
- `configurations[]` — one entry per build configuration. Single-config
  generators (Unix Makefiles, Ninja) produce exactly one; multi-config generators
  (Ninja Multi-Config, Visual Studio) produce several. The extractor reads
  `configurations[0]`.
- Within a configuration, `directories[]` and `targets[]`.

`directories[]` is a **tree**, expressed with `parentIndex` / `childIndexes` into
the same array. Each entry gives a directory's `source` and `build` path. This is
the structure Stage 4 walks to find third-party regions.

`targets[]` is a **flat list** of `{name, id, directoryIndex, jsonFile}` — just
enough to identify a target and find its detail file.

**Use in extraction.** Stage 1 reads `paths` to learn the source and build roots.
Stage 4 walks `directories[]` to decide which directories belong to a
third-party dependency. Stage 2 iterates `targets[]` to load every target file.

Directory 1 is `build/_deps/fmt-src` — a dependency's *source* directory sitting
**inside the build tree**, because that is where FetchContent unpacks it. No
containment test can separate it from genuinely generated code, which is exactly
why Stage 4 works from this tree rather than from path prefixes.

The target list is also longer than the project's own targets: `include(CTest)`
adds 28 bookkeeping targets (`Nightly*`, `Continuous*`, `Experimental*`),
trimmed from the sample above. They are harmless — nothing links them, so they
never enter a closure — but a tool that assumes every target is interesting will
trip over them.

## 1.4 `target-*.json`

**Written by:** CMake File API, one per target · **Read at:** Stages 2, 5, 6, 7, 8, 9

**Purpose.** To describe one target completely: what it is, where it came from,
what it links, what it compiles, and what it produces. This is the most-read
format in the pipeline — six stages each extract a different field.

**Structure.** The fields the extractor uses, in the order the stages need them:

| Field | Type | Meaning |
|---|---|---|
| `name` | string | the target's CMake name; also names its `<name>.dir/` build directory |
| `id` | string | `<name>::@<hash>` — the stable identity link edges refer to |
| `type` | string | `EXECUTABLE`, `STATIC_LIBRARY`, `OBJECT_LIBRARY`, `INTERFACE_LIBRARY`, … |
| `paths.source` | path | the directory that *defined* the target, relative to the source root |
| `dependencies[].id` | list | the targets this one links — the edges of the target graph |
| `sources[].path` | list | every file listed for the target, compiled or not |
| `sources[].compileGroupIndex` | int or null | **null means not compiled** — a header listed in `add_executable()` |
| `compileGroups[].includes[].path` | list | the `-I` roots, in search order |
| `compileGroups[].languageStandard.standard` | string | `"17"` — carried into the emitted `CMakeLists.txt` |
| `artifacts[].path` | list | what the target produces, relative to the build root |

**Use in extraction**, stage by stage:

- **Stage 2** indexes the file by `id`, by `name`, and by `directoryIndex`.
- **Stage 5** follows `dependencies[].id` to walk the target closure.
- **Stage 6** resolves `paths.source` against the source root and asks whether it
  falls in a third-party region — that single test decides copy-versus-re-declare.
- **Stage 7** matches `artifacts[].path` against the command CTest reports, tying
  a registered test back to the target that produces it.
- **Stage 8** collects `compileGroups[].includes[].path` as include roots and
  reads the language standard.
- **Stage 9** takes `sources[]` entries with a non-null `compileGroupIndex`.

```json
{
  "artifacts": [
    {
      "path": "apps/guess/guess"
    }
  ],
  "compileGroups": [
    {
      "includes": [
        {
          "path": "…/libs/input/include"
        },
        {
          "path": "…/build/_deps/fmt-src/include"
        },
        {
          "path": "…/libs/rng/include"
        },
        {
          "path": "…/build/generated"
        }
      ],
      "language": "CXX",
      "languageStandard": {
        "standard": "17"
      }
    }
  ],
  "dependencies": [
    {
      "id": "fmt::@976f4f0bee90b99ecdb6"
    },
    {
      "id": "rng::@56f3092fcbc80f32493b"
    },
    {
      "id": "input::@6d945ddea8f4ec024c33"
    }
  ],
  "id": "guess::@bba4818aa150d7f5ff20",
  "name": "guess",
  "nameOnDisk": "guess",
  "paths": {
    "build": "apps/guess",
    "source": "apps/guess"
  },
  "sources": [
    {
      "compileGroupIndex": 0,
      "path": "apps/guess/src/main.cpp"
    }
  ],
  "type": "EXECUTABLE"
}
```

**How the other target kinds differ.** Only the distinguishing fields are shown.

A **static library** produces an archive:

```json
{
  "name": "rng",
  "type": "STATIC_LIBRARY",
  "artifacts": [
    {
      "path": "libs/rng/librng.a"
    }
  ]
}
```

A **test executable** produces a binary — this is the path Stage 7 matches:

```json
{
  "name": "input_test",
  "type": "EXECUTABLE",
  "artifacts": [
    {
      "path": "libs/input/input_test"
    }
  ]
}
```

An **OBJECT library** produces no archive at all. Its `artifacts[]` lists the
individual object files, so a test command can never match one. Its sources are
still folded into whatever links it, exactly like a static library:

```json
{
  "name": "corecodec",
  "type": "OBJECT_LIBRARY",
  "artifacts": [
    {
      "path": "libs/core/codec/CMakeFiles/corecodec.dir/src/codec.cpp.o"
    }
  ]
}
```

A **third-party target** looks ordinary. The only field that gives it away is
`paths.source`, and only because of where it points:

```json
{
  "name": "fmt",
  "type": "STATIC_LIBRARY",
  "paths": {
    "build": "_deps/fmt-build",
    "source": "build/_deps/fmt-src"
  }
}
```

**Gotcha: the target that has no file.** `samples/basic` has a fifth first-party
target that appears nowhere in Part 1:

```cmake
add_library(build_info INTERFACE)
target_include_directories(build_info INTERFACE ${CMAKE_CURRENT_BINARY_DIR}/generated)
```

Every application links it. There is **no `target-build_info-*.json`**, and
`build_info` is absent from the codemodel's `targets[]` entirely. An `INTERFACE`
library compiles nothing and produces nothing, so the codemodel has nothing to
report; it is likewise absent from every `dependencies[]` list, which records
build ordering.

A closure built from the target graph alone would therefore silently lose its
generated header. The depfiles in [Part 4](#42-the-od-depfile) are what recover
it — and this is the clearest argument for reading two independent sources of
truth rather than trusting either alone.

## 1.5 `directory-*.json`

**Written by:** CMake File API, one per directory · **Read at:** not currently read

**Purpose.** Per-directory detail: install rules, and backtraces to the commands
that created them.

**Structure.** Small. `paths` restates the directory's source and build paths;
`installers[]` (empty here) would list install rules.

**Use in extraction.** None today — everything the extractor needs about
directories is already in the codemodel's `directories[]` tree. It is documented
because it is prominent in the reply directory, and because install rules are the
natural place to look if extraction ever needs to reproduce them.

```json
{
  "backtraceGraph": {
    "commands": [],
    "files": [],
    "nodes": []
  },
  "installers": [],
  "paths": {
    "build": "libs/rng",
    "source": "libs/rng"
  }
}
```

# Part 2 — The command trace

**Written by:** `cmake --trace-expand --trace-format=json-v1 --trace-redirect=<file>`
· **Read at:** Stage 3

**Purpose.** To record *what CMake actually did*, as opposed to what its input
files say. This is the authority for the
[dependency boundary](GLOSSARY.md#4-this-project): which dependencies are
third-party, how each is declared, and what each target links.

**Structure.** **JSON Lines** — one JSON object per line, not a JSON array. Line
one is a version header; every other line is one **trace record**, one per
command CMake executed:

| Field | Meaning |
|---|---|
| `cmd` | the command name, e.g. `target_link_libraries` |
| `args` | its arguments, **already variable-expanded** |
| `file` | the `.cmake` or `CMakeLists.txt` file the call came from |
| `line` | the line within it (`line_end` too, for multi-line calls) |
| `frame`, `global_frame`, `time` | call-stack depth and timing — ignored |

**Why expansion matters.** `args` arrives fully resolved, after `if()`,
`foreach()`, and function calls have run. A declaration written as
`FetchContent_Declare(${dep} ...)`, one made inside a wrapper function, or one a
tool like CPM synthesises internally all arrive here as plain arguments. Nothing
that reads the *text* of a `CMakeLists.txt` can follow any of those.
`samples/complex_deep` exercises exactly this:

```cmake
# Wrapped in a function: the declaration only exists once declare_json() runs.
function(declare_json)
  FetchContent_Declare(
    nlohmann_json
    GIT_REPOSITORY https://github.com/nlohmann/json.git
    GIT_TAG        v3.11.3
    GIT_SHALLOW    TRUE
  )
endfunction()
```

That declaration exists only while `declare_json()` runs. Stage 3 sees it anyway.

**Use in extraction.** Stage 3 keeps three command names and discards the rest:

- `FetchContent_Declare` → regenerated into the emitted `CMakeLists.txt`
- `find_package` → re-emitted verbatim, for the host toolchain to satisfy
- `target_link_libraries` → the per-target link tokens

This run produced **1904 lines**. Four records, with the ignored fields
removed:

```json
{"cmd": "FetchContent_Declare", "args": ["fmt", "GIT_REPOSITORY", "https://github.com/fmtlib/fmt.git", "GIT_TAG", "10.2.1", "GIT_SHALLOW", "TRUE"], "file": "…/CMakeLists.txt", "line": 12}
{"cmd": "target_link_libraries", "args": ["guess", "PRIVATE", "input", "rng", "fmt::fmt", "build_info"], "file": "…/apps/guess/CMakeLists.txt", "line": 2}
{"cmd": "target_link_libraries", "args": ["input", "PUBLIC", "fmt::fmt"], "file": "…/libs/input/CMakeLists.txt", "line": 3}
{"cmd": "find_package", "args": ["Git", "QUIET"], "file": "/usr/share/cmake-3.28/Modules/FetchContent.cmake", "line": 1635}
```

**Gotcha: the trace sees the dependencies' commands too.** The first three
records above are kept. The fourth is **rejected**, and it is a genuine
`find_package` — but its `file` is inside CMake's own bundled modules, where
`FetchContent.cmake` looks for Git so it can clone. Re-emitting it would make the
extracted tree demand Git for no reason at all.

Stage 3 therefore filters on `file`, not on `cmd`: a record counts only when it
came from the project's own CMake code, outside every third-party region. This is
why Stage 4 has to establish the regions before Stage 3 can finish.

# Part 3 — The CTest registry

**Written by:** `ctest --show-only=json-v1` (to stdout) · **Read at:** Stage 7

**Purpose.** To answer "what is actually a test?" A target *named* `input_test`
is not a test; a target an `add_test()` call registered is. Only CTest knows the
difference.

**Structure.** A single JSON document. `tests[]` is the useful part — each entry
has a `name` (as registered, which need not match the target name), a `command`
array whose first element is the absolute path to the executable, and
`properties[]` such as `WORKING_DIRECTORY`. A `backtraceGraph` (omitted below)
maps each test back to the `add_test()` call that created it.

**Use in extraction.** Stage 7 resolves `command[0]` and matches it against every
target's `artifacts[].path`. That recovers the owning target without assuming any
naming convention, so a test target called anything at all is still found. Stage 7
then keeps a test only if every first-party target it links is already in the
closure — which is what stops carrying tests over from enlarging the tree.

```json
{
  "kind": "ctestInfo",
  "version": {
    "major": 1,
    "minor": 0
  },
  "tests": [
    {
      "name": "rng_test",
      "command": [
        "…/build/libs/rng/rng_test"
      ],
      "properties": [
        {
          "name": "WORKING_DIRECTORY",
          "value": "…/build/libs/rng"
        }
      ]
    },
    {
      "name": "input_test",
      "command": [
        "…/build/libs/input/input_test"
      ],
      "properties": [
        {
          "name": "WORKING_DIRECTORY",
          "value": "…/build/libs/input"
        }
      ]
    }
  ]
}
```

**Gotchas.** A test whose command is a shell script or an external program matches
no artifact and is skipped — correctly, since the extractor could not rebuild it
from codemodel data anyway. And this format requires the build to be configured,
not merely present: CTest reads the generated test files, so an unconfigured tree
reports nothing.

# Part 4 — Compiler artifacts

Everything in Parts 1–3 comes from CMake. This part comes from the **compiler**,
and it is what makes the extraction minimal rather than merely correct: CMake
knows which files are compiled, but only the compiler knows which headers each
one actually pulled in.

## 4.1 `flags.make`

**Written by:** the Unix Makefiles generator · **Read at:** not read

**Purpose.** To hold the compile flags for one target, so the generated makefiles
can reference them by variable.

**Structure.** A Makefile fragment: `CXX_DEFINES`, `CXX_INCLUDES`, `CXX_FLAGS`.

**Use in extraction.** None — `CXX_INCLUDES` restates
`compileGroups[].includes[]`, which Stage 8 already reads from the codemodel, and
this file does not exist under Ninja. It earns its place here because it makes
one crucial fact visible in a single line:

```make
# CMAKE generated file: DO NOT EDIT!
# Generated by "Unix Makefiles" Generator, CMake Version 3.28

# compile CXX with /usr/bin/c++
CXX_DEFINES = 

CXX_INCLUDES = -I…/libs/input/include -I…/build/_deps/fmt-src/include -I…/libs/rng/include -I…/build/generated

CXX_FLAGS = -MMD -std=gnu++17
```

**Gotcha, and it is the important one.** fmt's include directory sits among the
first-party ones, passed as a plain **`-I`, not `-isystem`**. FetchContent brings
a dependency in via `add_subdirectory()`, so its targets are ordinary targets and
its include directories are ordinary include directories.

The consequence lands in the depfiles below: fmt's headers *do* appear there. So
"is this header in a depfile?" cannot decide what is third-party — that question
needs the regions from Stage 4. `-MMD` in `CXX_FLAGS` is what asks for the
depfiles in the first place.

## 4.2 The `*.o.d` depfile

**Written by:** `g++ -MMD`, one per translation unit · **Read at:** Stage 10

**Purpose.** To record the exact set of headers one translation unit included,
transitively, after the preprocessor resolved every `#if` and every include path.
This is the [header closure](GLOSSARY.md#4-this-project), and it is ground truth:
the compiler is reporting what it did, not predicting what it might do.

**Structure.** A **Makefile rule**, not JSON:

- the object file, then `:`
- then its prerequisites — the source, then every header — separated by
  whitespace, with `\`-newline continuations for readability

Parsing it is three steps, and `parse_depfile()` is three lines: join the
continuations, drop everything up to the first `:`, split on whitespace.

**Use in extraction.** Stage 10 globs `**/CMakeFiles/<target>.dir/**/*.o.d` for
every contributing target, parses each, discards sources and anything inside a
third-party region, and keeps the rest as that origin's headers. Stage 11 then
places them.

The `guess` translation unit:

```make
apps/guess/CMakeFiles/guess.dir/src/main.cpp.o: \
 …/apps/guess/src/main.cpp \
 …/build/_deps/fmt-src/include/fmt/color.h \
 …/build/_deps/fmt-src/include/fmt/format.h \
 …/build/_deps/fmt-src/include/fmt/core.h \
 …/build/_deps/fmt-src/include/fmt/core.h \
 …/build/generated/build_info.hpp \
 …/libs/input/include/input/input.hpp \
 …/libs/rng/include/rng/rng.hpp
```

Two things to read off it. `build_info.hpp` is here — the generated header from
the `INTERFACE` library that Part 1 could not see, recovered precisely because
the compiler really did include it. And `fmt/core.h` appears **twice**, once per
inclusion path, which is why `parse_depfile()` returns a set.

A smaller one — `rng` includes only its own public header:

```make
libs/rng/CMakeFiles/rng.dir/src/rng.cpp.o: \
 …/libs/rng/src/rng.cpp \
 …/libs/rng/include/rng/rng.hpp
```

And one from `complex_deep`, showing a **private header**:

```make
libs/core/CMakeFiles/core.dir/src/util.cpp.o: \
 …/libs/core/src/util.cpp \
 …/libs/core/include/core/core.hpp \
 …/libs/core/src/internal.hpp
```

`internal.hpp` is reached by a file-relative `#include "internal.hpp"` from a
source beside it, not through any include root. Stage 11 places it in
`src/<origin>/` next to that source rather than in `include/`, which is what
keeps the quoted include resolving.

**Gotchas.**

*The glob is `*.o.d`, not `*.d`.* CMake ≥ 4.0 writes a link-step depfile named
`link.d` into the same `.dir/`, listing object files and libraries rather than
headers. Matching `*.d` would feed those into the header closure.

*No depfile, no headers.* If a translation unit was compiled without `-MMD`,
Stage 10 finds nothing for it and copies none of its headers — and the failure
surfaces much later, as a missing `#include` in the standalone build. This is why
`-MMD` is a documented prerequisite rather than a nicety.

*System headers are excluded.* `-MMD` omits them by design (`-MD` would include
them). None of the depfiles in this build mention `/usr/include`, which is what
keeps the extractor from trying to copy the standard library.

## 4.3 `link.txt`

**Written by:** the Unix Makefiles generator · **Read at:** not read

**Purpose.** The exact command that links one target.

**Structure.** A single shell command line.

**Use in extraction.** None. It is here because it shows, in one line, precisely
what [folding in](GLOSSARY.md#4-this-project) replaces:

```sh
/usr/bin/c++ -MMD CMakeFiles/guess.dir/src/main.cpp.o -o guess  ../../libs/input/libinput.a ../../libs/rng/librng.a ../../_deps/fmt-build/libfmt.a
```

Three `.a` archives are linked. In the extracted tree there are no first-party
archives at all: `libinput.a` and `librng.a` become sources compiled straight
into `guess`, and only `libfmt.a` survives — rebuilt from the re-declared
dependency rather than copied.

# Part 5 — `CMakeLists.txt` as input

**Written by:** humans · **Read at:** never

This is the format the extractor deliberately **does not** parse, and saying so
precisely is worth more than a listing.

**Why not.** `CMakeLists.txt` is a program, not a manifest. `target_link_libraries`
takes generator expressions; variables and functions are expanded at configure
time; `if()` branches mean the file describes a *family* of builds rather than
one. Reading it correctly would mean reimplementing CMake — and reading it
incorrectly is worse, because the failure is silent and configuration-dependent.

**What replaces it.** Everything a `CMakeLists.txt` would have told you is
available *after* CMake has run it, in a form that already accounts for every
expansion and branch:

| You might want to read | Read this instead |
|---|---|
| `add_executable` / `add_library` | codemodel `targets[]` |
| `target_link_libraries` | `dependencies[]`, plus trace records for the tokens |
| `target_include_directories` | `compileGroups[].includes[]` |
| `FetchContent_Declare` | trace records |
| `add_test` | the CTest registry |
| `configure_file` | the generated file itself, via the depfiles |

The samples in this repository are shaped to make the difference biting rather
than theoretical: `samples/complex_deep` declares Boost in an `include()`d file
and nlohmann_json inside a function (Part 2). A text scan of the top-level
`CMakeLists.txt` finds neither. The trace finds both.

**The one exception.** `--deps-file <glob>` text-scans files for
`FetchContent_Declare` blocks, as an escape hatch for a declaration guarded
behind an `if()` the trace never enters. It is opt-in, documented as a last
resort, and carries exactly the fragility described above.

# Part 6 — `CMakeLists.txt` as output

**Written by:** the extractor, `write_cmakelists()` · **Stage:** 12

**Purpose.** To be the one file that makes the extracted tree a buildable
project. Everything else the extractor copies is payload; this file is what turns
a directory of sources into a build.

**Structure.** Emitted in a fixed order, each part conditional on what the
closure actually needs:

1. `cmake_minimum_required` and `project(<target>_standalone)`
2. the C++ standard, from `compileGroups[].languageStandard`
3. `include(FetchContent)` plus one regenerated `FetchContent_Declare` block per
   third-party dependency, then a single `FetchContent_MakeAvailable`
4. each `find_package()` call, re-emitted verbatim
5. `add_executable(<target> …)` listing every folded-in source
6. `target_include_directories(<target> PRIVATE include generated)` — only the
   directories that actually received files
7. `target_link_libraries(<target> PRIVATE …)` — only the third-party tokens
8. with `--with-tests`: `enable_testing()`, then per test an `add_executable`,
   its own include and link lines, and an `add_test()` preserving the registered
   name

Parts 3, 4, 7 and 8 are omitted entirely when empty — which is why the
no-dependency case produces a file with no `FetchContent` section and no
`target_link_libraries` at all.

**The richest example**, `guess` with `--with-tests`:

```cmake
cmake_minimum_required(VERSION 3.20)
project(guess_standalone LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

include(FetchContent)
FetchContent_Declare(
  fmt
  GIT_REPOSITORY https://github.com/fmtlib/fmt.git
  GIT_TAG 10.2.1
  GIT_SHALLOW TRUE
)
FetchContent_MakeAvailable(fmt)

add_executable(guess
  src/guess/src/main.cpp
  src/input/src/input.cpp
  src/rng/src/rng.cpp
)
target_include_directories(guess PRIVATE include generated)
target_link_libraries(guess PRIVATE fmt::fmt)

enable_testing()

add_executable(input_test
  src/input/src/input.cpp
  src/input_test/test/input_test.cpp
)
target_include_directories(input_test PRIVATE include generated)
target_link_libraries(input_test PRIVATE fmt::fmt)
add_test(NAME input_test COMMAND input_test)

add_executable(rng_test
  src/rng/src/rng.cpp
  src/rng_test/test/rng_test.cpp
)
target_include_directories(rng_test PRIVATE include generated)
add_test(NAME rng_test COMMAND rng_test)
```

Read against Part 1: `input` and `rng` have ceased to exist as targets, and their
sources are compiled directly into `guess` — and again into each test, because
the archives that used to be shared are gone. `fmt` returns as a regenerated
declaration rather than a copy. `generated/` holds `build_info.hpp`, the header
no target file ever mentioned.

**How the five outputs differ.** Same generator, same rules; all the variation
comes from what each application links:

| Sample | App | Folded in | FetchContent | find_package | Tests |
|---|---|---|---|---|---|
| basic | `guess` | input, rng | fmt | — | 2 |
| basic | `roller` | rng | fmt | — | 1 |
| basic | `greeter` | input | fmt | — | 1 |
| basic | `tally` | rng | — | — | 1 |
| complex_deep | `report` | core, corecodec, jsonio, textutil | boost, nlohmann_json | — | 3 |

Two rows are worth opening.

**`tally` — nothing to re-declare.** No `FetchContent` section, no
`target_link_libraries`. Its build directory never grows a `_deps/`, so the tree
configures and builds with no network access at all — while
`generated/build_info.hpp` is still present:

```cmake
cmake_minimum_required(VERSION 3.20)
project(tally_standalone LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(tally
  src/rng/src/rng.cpp
  src/tally/src/main.cpp
)
target_include_directories(tally PRIVATE include generated)

enable_testing()

add_executable(rng_test
  src/rng/src/rng.cpp
  src/rng_test/test/rng_test.cpp
)
target_include_directories(rng_test PRIVATE include generated)
add_test(NAME rng_test COMMAND rng_test)
```

**`report` — structure preserved, and a large dependency declined.** `core`
contains `src/util.cpp` *and* `src/detail/util.cpp`. Flattening would have
silently overwritten one with the other; Stage 11 keeps both, each at its path
relative to its origin target. `Boost::algorithm` shows the other half of Stage
6: the link line carries the imported-target name that was actually used, not a
`boost::boost` guess built from the declaration name:

```cmake
cmake_minimum_required(VERSION 3.20)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

FetchContent_Declare(

  URL https://github.com/boostorg/boost/releases/download/boost-1.87.0/boost-1.87.0-cmake.tar.gz

  DOWNLOAD_EXTRACT_TIMESTAMP TRUE
)
FetchContent_Declare(
  nlohmann_json
  GIT_REPOSITORY https://github.com/nlohmann/json.git
  GIT_TAG v3.11.3
  GIT_SHALLOW TRUE
)
FetchContent_MakeAvailable(boost nlohmann_json)

add_executable(report
  src/core/src/core.cpp
  src/core/src/detail/util.cpp
  src/core/src/util.cpp
  src/corecodec/src/codec.cpp
  src/jsonio/src/jsonio.cpp
  src/report/src/main.cpp
  src/textutil/src/textutil.cpp
)
target_include_directories(report PRIVATE include generated)
target_link_libraries(report PRIVATE nlohmann_json::nlohmann_json Boost::algorithm)

enable_testing()

add_executable(core_test
  src/core/src/core.cpp
  src/core/src/detail/util.cpp
  src/core/src/util.cpp
  src/core_test/test/core_test.cpp
)
target_include_directories(core_test PRIVATE include generated)
add_test(NAME core_test COMMAND core_test)

add_executable(jsonio_test
  src/core/src/core.cpp
  src/core/src/detail/util.cpp
  src/core/src/util.cpp
  src/jsonio/src/jsonio.cpp
  src/jsonio_test/test/jsonio_test.cpp
)
target_include_directories(jsonio_test PRIVATE include generated)
target_link_libraries(jsonio_test PRIVATE nlohmann_json::nlohmann_json)
add_test(NAME jsonio_test COMMAND jsonio_test)

add_executable(textutil_test
  src/core/src/core.cpp
  src/core/src/detail/util.cpp
  src/core/src/util.cpp
  src/textutil/src/textutil.cpp
  src/textutil_test/test/textutil_test.cpp
)
target_include_directories(textutil_test PRIVATE include generated)
target_link_libraries(textutil_test PRIVATE Boost::algorithm)
add_test(NAME textutil_test COMMAND textutil_test)
```

**What is missing is the point.** `samples/complex_deep` calls
`find_package(Threads REQUIRED)` at its top level, and Stage 3 records it — but
only `netsvc` ever linked `Threads::Threads`, and `netsvc` is outside `report`'s
closure. No link line names it, so Stage 8 does not re-emit it: an extracted
tree states the system dependencies it actually needs, not the ones its origin
repository happened to declare. `geom_test`, `netsvc_test` and `parsing_test`
drop out for the same reason, each reported as skipped.

Nor did Boost travel. Its 673 MB stays behind as the six-line
`FetchContent_Declare` above, pinned URL and hash intact; the deliverable is
**18 files, 176 KB**. That is the whole trade: a re-declared dependency is paid
for by whoever builds the tree, not by whoever ships it.

# Part 7 — Generated code

**Written by:** CMake's `configure_file()` at configure time · **Read at:** Stage 10, as an ordinary header

**Purpose.** To turn build-time facts — a version, a build type, a commit hash —
into a header the code can `#include`. It is the third category of input, next to
first-party and third-party: code the project owns but does not store.

**Structure.** A template with `@VAR@` placeholders, and the file CMake writes
from it:

```cpp
#pragma once

// This header is generated by CMake from cmake/build_info.hpp.in via
// configure_file(). It represents "generated code" that must be included in
// each application's dependency closure.
namespace build_info {
inline constexpr const char* version    = "@PROJECT_VERSION@";
inline constexpr const char* build_type = "@CMAKE_BUILD_TYPE@";
}  // namespace build_info
```

becomes, under `build/generated/`:

```cpp
#pragma once

// This header is generated by CMake from cmake/build_info.hpp.in via
// configure_file(). It represents "generated code" that must be included in
// each application's dependency closure.
namespace build_info {
inline constexpr const char* version    = "0.1.0";
inline constexpr const char* build_type = "";
}  // namespace build_info
```

**Use in extraction.** The extractor never reads the template and never re-runs
`configure_file()`. The *generated* header appears in the depfiles like any
other, so Stage 10 picks it up and Stage 11 places it under `generated/`, frozen
as a plain file. The emitted `CMakeLists.txt` adds `-I generated`, and the
`#include "build_info.hpp"` in the copied source resolves unchanged.

**Gotcha, and a design decision worth stating.** Freezing means the extracted
tree reports the version it was extracted *from*, forever — `0.1.0` above, not
whatever the standalone tree might call itself. For a build stamp that is the
honest answer. For a value that must stay live, the alternative is to copy the
`.in` template plus the `configure_file()` call instead of the output, which the
extractor does not currently do; it is noted in
[TUTORIAL.md §10](TUTORIAL.md) as a porting consideration.
